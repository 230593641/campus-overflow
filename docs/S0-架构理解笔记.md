# S0 · 架构理解笔记（对应 Issue #6、Issue #5）

> 交付物性质：S0 阶段要求的“架构理解笔记与调用链说明”。
> 阅读范围：`docs/adr/` 全部 8 条 ADR、README 第 7 节、`docs/错误码.md`、Identity 上下文全部非测试源码。

## 1. 两条必答问题

### 1.1 为什么用事务性发件箱（Transaction Outbox）

**问题**：`采纳回答` 一个动作要触发声誉记账、徽章授予、悬赏结算、搜索投影、通知投递。三种朴素做法都不成立：

| 做法 | 为什么不行 |
| --- | --- |
| 在同一事务里同步调用下游上下文 | Q&A 硬依赖三个下游，一个下游异常就让“采纳”整体失败；响应时间叠加；跨上下文事务边界被打穿（违反 ADR-001 的边界约束） |
| 直接 `ApplicationEventPublisher.publishEvent` 异步发 | 事务回滚后事件已经发出（幽灵事件）；进程崩溃则事件永久丢失（丢事件），一致性无从保证 |
| `@TransactionalEventListener(AFTER_COMMIT)` | 只在提交后执行，进程崩溃就丢，且没有重试与可观测性 |

**本项目的做法（ADR-002）**：业务写入与事件写入 `outbox_event` 在**同一个本地事务**里提交——
要么“业务+事件”都成功，要么都不发生；随后 `OutboxRelay` 用 `FOR UPDATE SKIP LOCKED` 认领未投递事件，
按 id 顺序投递到进程内事件总线。语义是**至少一次**，因此**消费端必须幂等**：

- 声誉侧靠账本唯一键 `(event_id, user_id, reason)` 天然去重（ADR-004）；
- 投影侧靠 `processed_event` 表去重。

失败指数退避重试，超过 10 次进死信并以指标 `co_outbox_dead_letters` 告警。
**代价**：最终一致（演示时声誉会有几百毫秒延迟）、多一张表和一个后台任务。这是有意识的取舍，不是缺陷。

一句话：**用“同一事务内落事件”换“不丢事件”，用“消费端幂等”换“允许重复投递”。**

### 1.2 为什么领域层禁止框架依赖

**根因**：如果聚合上直接标 `@Entity`，JPA 的要求（无参构造、字段可变、延迟加载代理、`equals` 语义）就会反过来
塑造业务模型；更要命的是**测试一个业务规则要启动持久化上下文**，一套领域测试从毫秒变成几十秒，红→绿的反馈环断掉。

**本项目的做法（ADR-008，适应度函数 FF-1）**：

- `co-*/co-*-domain` 模块是**纯 Java**：只有 `java.*` 与 `co-shared-kernel`，没有任何 Spring / JPA / Jackson。
- 仓储**接口**定义在领域层（如 `CourseRepository`、`UserRepository`），实现（`*JpaRepository` + `*RepositoryAdapter` + `*JpaEntity`）在 infrastructure 层。
- 由 ArchUnit 自动检查：领域层出现框架注解即构建失败——**约束靠测试强制，不靠自觉**。

副作用（可接受）：每个聚合约 40 行映射样板；计数器字段（分数、回答数、浏览数）不由聚合回写，改用原子 `UPDATE`，避免“读-改-写”覆盖并发增量。

## 2. 8 条 ADR 速查

| ADR | 决策 | 一句话理由 |
| --- | --- | --- |
| 001 | 模块化单体 + 六边形分层（api/domain/application/infrastructure/interfaces） | 5 人 16 周、零运维、共享同一份数据 → 单一架构量子；边界由 Maven 依赖图 + ArchUnit 强制 |
| 002 | 跨上下文用事务性发件箱 | 不丢事件、下游故障不阻断主流程、至少一次 + 消费端幂等 |
| 003 | Redis 服务端会话而非 JWT | 要能**立即**封禁；HttpOnly 会话 Cookie 让 XSS 偷不到令牌；Redis 天然支持水平扩容共享 |
| 004 | 只追加的声誉账本 + 定期对账 | 每一分都可追溯到来源；`(event_id, user_id, reason)` 唯一键让重投天然幂等；FF-8 对账指标 |
| 005 | MySQL 8 ngram 全文索引 | 中文搜索零额外组件；`ngram_token_size=2` + 关闭停用词；封装在 `SearchPort` 后，可换 ES 或 Like 适配器对照 |
| 006 | 用户内容一律软删除（`deleted_at`） | 引用完整、可复核、可恢复；代价是所有查询必须显式带 `deleted_at IS NULL` |
| 007 | 前后端以 OpenAPI 契约协作 | 5 人并行开发，接口先定后写；错误统一 RFC 9457 Problem Details + 业务 `code`；分页 `{items,total,page,size}`；时间 UTC |
| 008 | 领域对象与 JPA 实体分离 | 领域模型不被框架绑架，领域测试毫秒级，换持久化只改适配器 |

## 3. User / Course / CourseMember 三个聚合怎么协作

- **User**（`co-identity-domain/.../domain/User.java`）：账号主体。负责注册创建、密码摘要、状态（`UserStatus`）、角色（学生/教师/管理员）与显示名唯一性。
- **Course**（`Course.java`）：课程，是“课程专属问答区”的载体。**不变式**：课程代码 2–20 位字母数字连字符、同一学期内代码唯一、只有教师/管理员能创建。
- **CourseMember**（`CourseMember.java`）：User × Course 的**成员关系**，是授权判定（谁能采纳、认证、悬赏）的依据。用独立的 `CourseRole` 而不是把角色塞进 `User`，因为同一个人在不同课程里可以是学生或助教。

三者关系：`Course` 只持有 `teacherId`（值引用，不持有 `User` 对象，避免跨聚合的强引用）；
`CourseMember` 持有 `courseId` + `userId`；要展示名字时由应用层批量查 `User` 再拼装视图（见 `CourseService.toViews`、
`CourseService.members` 用 `users.findAllById` 一次批量取，避免 N+1）。
**聚合之间只通过 id 引用、只在应用层编排**——这正是领域层能保持纯 Java 的原因。

关键业务规则（可直接对照单元测试）：

- 只有教师/管理员可创建课程（`ForbiddenException ID-3002`）；代码非法 `ID-1010`。
- 同一学期同代码课程冲突（`ConflictException ID-2004`）；重复加入课程 `ID-2005`；不是成员却改角色 `ID-4003`。
- 课程教师角色不可被降级（`BusinessRuleException ID-1013`）。

## 4. 调用链

### 4.1 注册（注册 → 落库 → 发事件 → 审计）

```
POST /api/v1/auth/register
 └─ AuthController.register(RegisterRequest)                       co-identity-interfaces
     └─ UserRegistrationService.register(RegisterUserCommand)      @Transactional  co-identity-application
         ├─ PasswordPolicy.validate(password)                      领域层纯函数（密码策略）
         ├─ User.register(...)                                     领域工厂：规范化 + 业务校验
         ├─ ensureUnique(user)                                     users.existsBy{Username,DisplayName,Email}
         │                                                         → ConflictException ID-2001/2002/2003
         ├─ UserRepository.save(user)                              → UserRepositoryAdapter → UserJpaRepository
         ├─ IntegrationEventPublisher.publish(UserRegisteredEvent)  落 outbox_event（同一事务！ADR-002）
         └─ AuditTrail.record("USER_REGISTERED", ...)              审计，账号用 Masking.account 脱敏
```

### 4.2 登录（限流 → 认证 → 轮换会话 → 存上下文）

```
POST /api/v1/auth/login
 └─ AuthController.login(LoginRequest)
     ├─ LoginThrottle.isBlocked(username)                          Redis 计数：1 分钟 5 次 → LockedException
     ├─ AuthenticationManager.authenticate(...)                    Spring Security
     │   └─ DaoAuthenticationProvider
     │       ├─ DbUserDetailsService.loadUserByUsername(username)   → UserRepository 查用户
     │       └─ BCryptPasswordHasher.matches(raw, hash)             PasswordHasher 端口的基础设施实现
     ├─ 失败 → throttle.recordFailure + authAudit.loginFailed + BadCredentialsException
     ├─ 成功 → throttle.reset
     ├─ request.changeSessionId()                                  防会话固定
     ├─ SecurityContextRepository.saveContext(...)                  Spring Session 写入 Redis
     └─ userQuery.me(userId) → MeView                              返回当前用户视图
```

要点：**认证状态在 Redis 的会话里，不在前端令牌里**（ADR-003）；封禁只需删除会话，会话即刻失效。
被保护接口通过 `Actor` 参数注入（`ActorAware`），领域层只依赖 `co-shared-kernel` 的 `Actor`，不依赖 Spring Security 类型。

### 4.3 建课（教师视角）

```
POST /api/v1/courses
 └─ CourseController
     └─ CourseService.create(actor, CreateCourseCommand)           @Transactional
         ├─ Course.create(actor, code, name, term, now)            仅教师/管理员；代码正则；名称/学期长度
         ├─ courses.existsByCodeAndTerm(code, term)                冲突 → ConflictException ID-2004
         ├─ CourseRepository.save(course)                          → CourseJpaEntity
         └─ CourseRepository.saveMember(CourseMember.teacher(id))  创建者自动成为 TEACHER 成员
```

### 4.4 加人（学生自助加入 / 教师任命助教）

```
POST /api/v1/courses/{id}/join           → CourseService.join(actor, courseId)
    ├─ loadCourse（不存在 → NotFoundException ID-4002）
    ├─ findMember 已存在 → ConflictException ID-2005
    └─ saveMember(CourseMember.student(courseId, userId, now))

POST /api/v1/courses/{id}/members/{userId}/role → CourseService.assignRole(actor, courseId, userId, role)
    ├─ 非管理员且非该课教师 → ForbiddenException ID-3003
    ├─ 非成员 → NotFoundException ID-4003
    └─ member.changeRole(role)  教师不可降级（ID-1013）→ saveMember
```

### 4.5 跨上下文的唯一入口

其它三个上下文**只能**依赖 `IdentityApi`（`co-identity-api`），实现是 `IdentityApiImpl`（application 层）——
拿到的是 `UserSummary` / `CourseSummary` 这类**只读契约**，而不是 `User` 实体。这是 ADR-001 里“跨上下文只经 api”的落地方式。

## 5. 这套理解对 S2 / S3 的直接影响

| 约束 | 写 TODO 时的含义 |
| --- | --- |
| 领域层零框架依赖（FF-1） | Q&A / Reputation / Discovery 的聚合里不能出现 `@Entity` / `@Service`；时间只从方法参数 `Instant now` 进来，不调 `Instant.now()` |
| 事件与业务同事务（ADR-002） | 应用层负责 `events.publish(...)`，领域层只产出事实；重复投递要靠唯一键/`processed_event` 兜住 |
| 声誉只追加（ADR-004） | `ReputationAccount` 只做余额守卫与冻结/解冻，流水由应用层写入 |
| 软删除（ADR-006） | 删除是 `softDelete()` + `ensureNotDeleted()`（`Answer`/`Question` 的 TODO 里各有一个），不是物理移除 |
| 错误码契约（`docs/错误码.md`） | 抛 `BusinessRuleException("QA-1005", ...)` 这类带分段码的异常，不要自造码 |
| 中文学搜索（ADR-005） | `SearchQuery` / `DiscoveryQueryService` 的词项要按 ngram 规则切分与去重 |
